DataShield — Architectural Review: Layers 1–3
This is a senior-engineer review traced against the actual code, not the docs. I'll walk through ingestion → preprocessing → feature engineering, then critique what works and what doesn't.

0. Big Picture: How the Three Layers Are Wired
The three layers are not chained together inside the pipeline. They're glued together by the API layer (api.py::_classify). That's the single most important architectural fact in this codebase, and it shapes everything below.
                  ┌──────── app.py (Streamlit UI) ────────┐
                  │  st.file_uploader → POST /classify/* │
                  └────────────────┬──────────────────────┘
                                   ▼
                         api.py  (FastAPI)
                                   │
        ┌──────────────────────────┼───────────────────────────┐
        ▼                          ▼                           ▼
  /classify/file            /classify/batch              /classify
   (single)                  (async N files)              (raw text)
        │                          │                           │
        ▼                          ▼                           │
  extract_text_from_bytes()  (per-file, in a loop)             │
   = LAYER 1                                                   │
        │                          │                           │

Layer 3 in this codebase is inspection-only. The classifier doesn't consume the FeatureSummary — it owns its own featurization inside LogisticModel and XGBoostModel. We'll come back to this; it's both a strength (separation of concerns) and a weakness (Layer 3 is decorative for inference).

1. Layer 1 — Ingestion (ingestion.py)
What it actually does
A single-file module with two public functions:

extract_text_from_file(file_path, filename) — path-based, used by no production caller (legacy/unused).
extract_text_from_bytes(file_bytes, filename) — bytes-based, the only one actually called in production (by api.py lines 255 and 343).

Both return (text, metadata) where metadata is just {source_file, file_type, size_bytes, char_count, word_count}.
Supported formats
SUPPORTED_FORMATS = ['.pdf', '.docx', '.doc', '.txt', '.md', '.csv', '.json', '.jsonl', '.html', '.htm', '.rtf', '.log']
Dispatch is a flat if/elif chain on file extension. Each format has a private extractor:
FormatLibraryFallbackPDFpdfplumberpypdfDOCXpython-docx—HTMLBeautifulSoupregex stripCSVstdlib csv.DictReader—JSON/JSONLstdlib json + line-by-line fallback—TXT/MD/LOG/RTFplain UTF-8 read—
Failure is non-fatal: exceptions are caught, text = "[Extraction failed: ...]" is returned, and metadata['extraction_error'] is set. The pipeline keeps moving.
Execution flow for an upload
A user drops payroll.pdf into the Streamlit uploader at app.py:366:

app.py:399 — f.read() reads the bytes; they're posted to POST /classify/file as multipart.
api.py:254 — data = await file.read() re-buffers bytes from Starlette's UploadFile.
api.py:255 — extract_text_from_bytes(data, file.filename) is called.
Inside extract_text_from_bytes, the extension .pdf routes to _extract_pdf_bytes, which wraps the bytes in io.BytesIO and tries pdfplumber first.
Returns (text, {source_file: 'payroll.pdf', file_type: 'pdf', size_bytes: ..., char_count: ..., word_count: ...}).
Optional metadata enrichment from form fields (source_system, department) at lines 259–262.

Async batch path (POST /classify/batch)
This is not true async — it's a FastAPI BackgroundTasks worker:

Client uploads N files.
Loop at api.py:341–348: every file is read into memory and extracted synchronously, then accumulated into an items list.
A job_id is generated, persisted to logs/async_jobs.json, and background_tasks.add_task(_run_batch_job, ...) queues it.
_run_batch_job runs sequentially in the same event loop, classifying each item one at a time and writing progress to disk after every doc.
Client polls GET /classify/status/{job_id}.

Folder ingestion path (separate from the API)
utils/io_helpers.py::read_documents() is used by scripts/predict_cli.py for CLI folder ingestion. It walks a directory with p.rglob('*'), yields (text, metadata) tuples, but is restricted to .txt / .log / .md / .csv / .json / .jsonl and explicitly refuses PDF/DOCX with UNSUPPORTED_EXT_MSG. This is a separate, weaker ingestion code path that exists in parallel to ingestion.py — see weaknesses below.
Strengths

Single dispatch surface: one extension → one extractor. Easy to add a new format (one helper + one branch).
Resilient: extraction errors don't kill the request; they're tagged in metadata.
Two-path API (path/bytes) covers both Streamlit uploads and disk reads cleanly.
Library fallbacks (pdfplumber → pypdf, BeautifulSoup → regex) keep it deployable on slim images.

Weaknesses

No Apache Tika, no Kafka, no S3 — yet the architecture diagram (image 2) lists exactly those. The module's own docstring admits this: "No Kafka, no S3 — local file ingestion for laptop deployment." This is the largest gap vs the PS.
Two parallel ingestion code paths (ingestion.py and utils/io_helpers.py) with different supported-format sets. io_helpers.py refuses PDF/DOCX; ingestion.py handles them. CLI users and API users get inconsistent capabilities. This is technical debt waiting to be a bug.
Whole-file in-memory: await file.read() slurps the entire upload before any processing. A 200 MB PDF starves the worker.
No streaming, no chunked upload, no virus scan, no MIME validation — only extension-based dispatch. A user renaming malware.exe to report.pdf gets it parsed.
extract_text_from_file is dead code in production but maintained alongside extract_text_from_bytes with duplicated logic (the PDF/DOCX/HTML/CSV/JSON helpers all exist twice).
Async batch is not concurrent. BackgroundTasks runs in the same process, sequentially. For 100 files you get N × per-doc-latency, not parallelism.

2. Layer 2 — Pre-processing (preprocessing.py)
What it actually does
This is the cleanest, most well-designed layer in the project. It exposes one function:
pythonpreprocess(text, metadata) -> PreprocessedDoc
PreprocessedDoc is a dataclass holding three parallel views of the text:

raw_text — original, untouched. What the policy engine and classifier see.
clean_text — normalized. What feature engineering and TF-IDF see.
masked_text — PII replaced with <EMAIL>, <US_SSN>, etc. What the audit log sees.

This separation is the architectural insight of the layer: the same document has different audiences with different trust levels, and they each get the appropriate view.
Execution flow inside preprocess()
For an input text like "Employee SSN 123-45-6789, salary $142,000, HR review.":

clean_text() (line 108) runs four sub-steps in order:

_unicode_normalize — NFKC normalization (handles width, ligatures; preserves Devanagari for Hindi).
_strip_control_chars — kills \x00–\x1f except newline/tab.
_strip_boilerplate — five regexes that nuke email quote lines (> ...), separators (----), "Sent from my iPhone", confidentiality footers, unsubscribe lines.
_collapse_whitespace — multi-space → single, multi-newline → double.


detect_language(cleaned) (from utils/language_detector.py) — pure Unicode-script counting. If ≥15% Devanagari → 'hi'; if ≥85% Latin → 'en'; else 'unknown'. O(n), deterministic, no model dependency.
masker.mask(cleaned) — calls the singleton from utils/presidio_masker.py:

Primary: Microsoft Presidio (AnalyzerEngine + AnonymizerEngine), constrained to a fixed entity list (US_SSN, CREDIT_CARD, IBAN_CODE, IN_PAN, IN_AADHAAR, EMAIL_ADDRESS, PHONE_NUMBER, etc.), threshold 0.4.
Fallback: if Presidio or its spaCy model isn't installed, transparently falls back to utils/pii_masker.py — eight regex patterns. The singleton caches Presidio's heavy init.


tokenize(cleaned) — regex \w+(?:'\w+)?. Cheap, deterministic, Unicode-aware (works for both EN and HI).
chunk_text(cleaned, max_tokens=480) — paragraph-aware greedy packing into ≤480-token chunks. Sized for BERT's 512-wordpiece cap.
infer_metadata(cleaned, metadata) — keyword scan of the first 2000 chars for source/department hints (e.g., 'salary' → 'HR', 'invoice' → 'Finance'). Fills UNKNOWN defaults. Attaches detected_language.
Returns the PreprocessedDoc. It also exposes a for_audit() method that strips raw_text/clean_text and gives only a masked preview + counts — used at api.py:202 so audit logs never see raw content.

How data moves out
After preprocess() returns at api.py:178:

pre.clean_text → feature_engineering.featurize(pre.clean_text, lang=pre.detected_language) at line 182.
pre.raw_text → clf.predict(pre.raw_text, pre.metadata, doc_id=doc_id) at line 188. The classifier deliberately gets raw text because the downstream PolicyEngine needs the live PII patterns to fire its "if Restricted token detected → override to Restricted" rule (system architecture image 3).
pre.for_audit() → embedded in the final response.

Schemas / contracts
The contract is the @dataclass PreprocessedDoc. It carries 11 fields + a to_dict() and a safe-for-audit for_audit() projection. Type hints are honest; Dict[str, Any] is only used for the loose metadata dict.
Strengths

Three-view design (raw / clean / masked) is the right model. Each downstream consumer gets the view it should have.
Idempotent clean_text — safe to call twice.
Presidio + regex defense-in-depth — exactly what the architecture image (3) calls for. Singleton avoids reloading spaCy.
Boilerplate patterns are conservative — they target high-confidence noise (signature lines, footers), not document content.
Hindi handled correctly — NFKC normalization preserves Devanagari, tokenizer regex is Unicode-aware, language detector is script-based.
for_audit() projection enforces Constraint C1 ("No raw PII stored post-classification") at the API boundary.

Weaknesses

The classifier doesn't actually use clean_text. _classify passes pre.raw_text to the pipeline (line 188). The cleaning helps feature engineering and audit, but the live prediction is on the unclean text. This is a deliberate choice (policy engine needs PII patterns) but it means cleaning gives a smaller lift than it appears.
Metadata inference is naive. _DEPT_HINTS = {'salary': 'HR', 'invoice': 'Finance'} is keyword-matching on the first 2000 chars. A finance email about an HR salary survey will be misclassified.
No PII span tracking. masker.mask() returns the masked text and entity types — but doesn't return spans/offsets. If a downstream consumer needed to know where PII was found in the original document, the information is gone.
Chunking is built but never consumed downstream. pre.chunks is computed eagerly but the only consumer is the API preview endpoint. The transformer model (which is what the 512-token limit was for) operates on whole texts elsewhere.
Boilerplate patterns are English-only. The Hindi route gets no equivalent stripping.
detect_language is called twice: once in preprocessing.preprocess, once inside pipeline.predict_batch._route. Cheap, but redundant — the pipeline could trust the metadata.

3. Layer 3 — Feature Engineering (feature_engineering.py)
Critical thing to understand first
This layer does not produce features that the classifier consumes. Read the module docstring carefully:

"The classifier module already does featurization internally — this layer wraps that with introspection: you can ask 'what features did doc X produce?' without running the full classifier."

The actual featurization for inference lives inside the models themselves:

LogisticModel (models/logistic_model.py) holds a sklearn.Pipeline([TfidfVectorizer, LogisticRegression]) — the vectorizer is part of the joblib artifact.
XGBoostModel (models/xgboost_model.py) holds a HashingVectorizer(n_features=512, ngram_range=(1,2)) + one-hot encoders for source_system / department / file_type + 4 numeric stats — all assembled in its private _featurize().
The transformer carries its own tokenizer.

feature_engineering.featurize() is a read-only mirror of those features, built for the UI's "Feature Preview" panel and the POST /features/preview API endpoint.
What featurize() actually returns
A FeatureSummary dataclass containing:

tfidf_top: List[(token, weight)] — top-k TF-IDF tokens for this doc, computed by reaching into the trained LogisticModel and calling its persisted TfidfVectorizer.transform([text]), then argsort-top-k.
unigram_count, bigram_count — whitespace-split counts.
numeric_features — {num_chars, num_tokens, num_digits, digit_ratio}. Mirrors what XGBoost uses, but recomputed (not shared).
embedding_dim, embedding_norm — populated only if a transformer artifact exists. Calls TransformerModel.encode([text]) if model.encode exists. Otherwise None.
vocab_size, used_language — bookkeeping.

Execution flow
For each request hitting _classify:

api.py:182 — feat = feature_engineering.featurize(pre.clean_text, lang=pre.detected_language, top_k=8).
Inside featurize():

tfidf_top_tokens(text, lang, top_k) calls _logistic_model_for_lang(lang), which lazy-loads the LogisticModel joblib from artifacts/en/logistic.joblib or artifacts/hi/logistic.joblib on first call. The result is cached in a function-attached dict (_logistic_model_for_lang._cache) — so the second request reuses it.
It reaches into model.pipeline.named_steps['tfidf'], calls vec.transform([text]), sorts the resulting sparse row, and returns the top-k indices.
_ngram_counts and _numeric_features are pure functions on the text.
embed_optional is tried (returns None unless a fine-tuned transformer artifact is present).


The summary becomes part of the API response (final['features'] = feat.to_dict() at line 203).

Strengths

Genuine introspection. The TF-IDF top-k is computed from the actual trained vectorizer, not a separate one. This is honest — what the UI shows is what the model literally sees.
Lazy + cached model loading. Module-attribute cache via _logistic_model_for_lang._cache keeps it cheap.
Graceful absence of transformer. embed_optional returns None if torch isn't installed or no artifact exists. No exceptions bubble up.
Separately addressable. Exposing POST /features/preview as a standalone endpoint lets compliance auditors inspect what the model would "see" without consuming a classification slot — and that's exactly what the architecture image-3 row "Feature Engineering" needs.

Weaknesses

It is conceptually a projection of the model, not a layer. A Layer in the PS sense is supposed to produce features for downstream models. This module instead re-derives them for display. The actual feature pipeline lives in LogisticModel.__init__ and XGBoostModel._featurize and is duplicated/inconsistent between them.
Tight coupling to LogisticModel's internals — model.pipeline.named_steps['tfidf'] is a hard dependency on a specific sklearn pipeline shape. If you ever swap LR for SGDClassifier with a different step name, this breaks silently.
TF-IDF "top tokens" is a poor proxy for what XGBoost or the transformer key on. The UI shows TF-IDF tops as if they're "the features," but the XGBoost ensemble member uses hashed features (no recoverable vocab) and metadata one-hots — none of which this summary surfaces. The auditor gets a misleading picture.
Triple-counted tokenization: this module's _ngram_counts uses text.split(); XGBoost's _numeric_features uses text.split(); preprocessing's tokenize uses a regex. Three slightly different definitions of "token" floating around.
Lang fallback unfair: if you ask for lang='hi' but no Hindi LR artifact exists, tfidf_top silently returns []. No telemetry. The UI just shows an empty list with no explanation.
embed_optional reloads the transformer on every call if not cached — it doesn't share the cache with the pipeline's already-loaded transformer. Two copies in memory in the worst case.

5. Cross-Cutting Architectural Assessment
Enterprise-level choices that are correct

Lazy pipeline loading with double-checked locking (api.py:74–85) — import-time is cheap, first request pays the cost. Correct for serverless and dev-loop ergonomics.
Defense-in-depth masking — Presidio primary + regex fallback + for_audit() projection. C1 (no raw PII persisted) is enforced at every write boundary.
Language routing as a first-class concept — separate model sets per language, separate artifact directories. Matches the architecture-image-3 row.
Idempotent, dataclass-based contracts between layers (PreprocessedDoc, FeatureSummary) — easier to test, easier to swap implementations.
force_mode='fast' at api.py:84 is a deliberate latency-vs-accuracy lever. The pipeline knows about it and reports runtime_mode in audit. This is exactly the kind of operational dial enterprise teams need.
Audit + override + approval logs as JSONL — append-only, replay-able, easy to migrate to a real store later.

Unnecessary complexity / duplication

Two ingestion paths (ingestion.py for API, utils/io_helpers.py for CLI) with diverging format support. They should be one.
Two copies of every PDF/DOCX/HTML/CSV/JSON extractor in ingestion.py (path-based and bytes-based) — collapse them via io.BytesIO.
Three near-duplicate "numeric features" definitions: feature_engineering._numeric_features, xgboost_model._numeric_features, preprocessing.tokenize. Tokens get redefined in three places.
detect_language called twice per request (preprocessing + pipeline routing). Cheap, but the second call should trust pre.detected_language from the metadata.
Boilerplate patterns live inline as a module-level constant in preprocessing.py. For an enterprise system they should be in configs/ with the policy/threshold tables — Constraint C2 requires auditability.

Architectural strengths

Single response object containing label + confidence + evidence + policy_action + preprocessing audit + feature summary + per-layer latency + audit metadata. One API call, complete trace. Excellent for compliance reviewers.
Per-layer latency telemetry in the response (latency_ms.preprocessing, latency_ms.features, latency_ms.classification). Saved my time when reviewing — this is rare and great.
Tests for each layer (tests/test_end_to_end.py, tests/test_language_detector.py, tests/test_latency_fix.py) — the test suite exists and exercises the integration points.

Architectural weaknesses

The whole "ingestion layer" promised by the architecture (Kafka/S3/Apache Tika) is absent. What ships is a REST upload handler and a per-format dispatcher. For a "scalable, automated mechanism" (PS line 1), this is the biggest gap. A laptop demo masquerading as an ingestion service.
Layer 3 is a mirror, not a layer. The PS calls Feature Engineering an independent layer; in this code it's an introspection wrapper. The real featurization is buried inside model classes and is not separately swappable. If you wanted to swap from hashing-vectorizer to SentenceTransformer embeddings for XGBoost, you'd have to edit xgboost_model.py, not a feature engineering module.
No streaming end-to-end. Everything is read-all-into-memory. PS expects "batch and real-time streams." This is real-time-only with a synchronous-loop pretending to be batch.
No content-type validation, no AV scan, no MIME sniff. Ingestion trusts the filename extension. C5 mentions mTLS — but ingestion-layer file safety isn't addressed at all.
Metadata layer is undercooked. PS lists source system, file type, author, department, creation date. We get source_system, department (both via keyword-hints), file_type — but author and creation date are never extracted from the document itself, even though PDF and DOCX carry them in their properties.

What should be improved (priority-ordered)

Make Layer 3 a real layer. Move LogisticModel's TfidfVectorizer and XGBoostModel._featurize into a shared feature_engineering.build_features(preprocessed_doc) -> FeatureMatrix and have the models accept the matrix as input. This makes featurization swappable and testable independently. The current "inspection" view becomes a free byproduct.
Collapse the two ingestion paths. Delete utils/io_helpers.py's ad-hoc reader; route the CLI through ingestion.extract_text_from_file. One source of truth for which formats are supported.
Extract author/creation-date from PDF/DOCX metadata. pdfplumber.PDF.metadata and python-docx.Document.core_properties.created/author are one-liners. The PS lists them; we currently throw them away.
Add a real async path. Either Celery + Redis or asyncio.gather over ThreadPoolExecutor. BackgroundTasks sequential loop is fine for demos, not for a payments-vendor production claim.
Move boilerplate patterns + dept/source hints into configs/ so they're versioned with the policy and pass audit (C2). Currently hard-coded.
Track PII spans, not just types. Presidio returns offsets — preserve them in PreprocessedDoc so the UI can highlight redactions. Today the offset information is computed by Presidio and immediately thrown away.
Replace extension-based dispatch with a proper MIME check (python-magic) before the extractor chain. Stops .pdf-renamed-malware at the door.
Cache the transformer in one place, not separately in pipeline._LanguageModelSet and feature_engineering.embed_optional.
